# SQL Executed During a Full Netezza Schema Refresh

This document describes the SQL generated by the current full metadata
prefetch for a Netezza connection (`CachePrefetcher.executeConnectionPrefetch`).
It covers the path run for the entire connection, for example after refreshing
the server node.

## How to Read the Examples

In the examples, `TEST_DB` is the exact value of one database returned by the
first SQL statement. The application does not apply a blanket `UPPER` or
`TRIM` to catalog values. A full refresh is not limited to the database used to
establish the initial connection: it first retrieves the list of databases and
then processes each live database separately.

For example, if `_V_DATABASE` returns `just_data`, the generated catalog SQL
uses a quoted qualifier and an exact predicate:

```sql
FROM "just_data".._V_OBJECT_DATA
WHERE DBNAME = 'just_data'
```

If the catalog value is `DATABASE ` (with a meaningful trailing space), the
qualifier and literal retain that space. This is deliberately different from a
database name typed by a user: unquoted `just_data` is interpreted by Netezza
as `JUST_DATA`, while quoted `"just_data"` means the exact lower-case name.

In the current implementation, the full refresh invokes the query builder with
an array containing one database (`[db]`). Therefore, the SQL actually sent
for this refresh does not contain `UNION ALL`; the ability to generate a UNION
remains only in the general builder used by other paths.

## Full Refresh Order

For a cold or forced refresh, the order is as follows:

1. once: the database list;
2. for each live database: schemas, followed by object type groups;
3. for each live database: regular objects, followed by external objects;
4. for each live database: procedures;
5. for each live database: regular columns; additionally, external table
   columns if stage 3 detected an `EXTERNAL TABLE` in that database.

The default metadata query concurrency limit is `1`. A full connection refresh
uses one primary physical Netezza session for databases, schemas, objects and
procedures. Its column stage can use the independently configured
`justybase.metadata.fullRefreshColumnConnections` pool (default `1`, maximum
`8`) to process independent databases in parallel. Queries for one database
remain serial, and a failed optional session falls back to the primary session.
The existing `justybase.metadata.queryConcurrency` setting continues to govern
ordinary metadata and warm-up requests; it is not used to multiply the full
refresh column pool.

## 0. Technical Session-Identification Query

At the start of the full refresh, its scoped metadata connection executes:

```sql
SELECT CURRENT_SID
```

This is used for timing attribution and, when necessary, metadata session
cleanup. It is not a catalog query and does not return schema data. The value
is reused by all SQL statements on one physical session, so it is executed
once rather than once per catalog query. The primary connection is opened for
the refresh; additional column-pool connections are opened lazily only when
there are enough databases to process and are closed with the primary session.
Netezzy driver startup queries that are not generated by the repository are not
included in this document.

## 1. Database List — Once per Full Refresh

Source: `NZ_QUERIES.LIST_DATABASES`.

```sql
SELECT DATABASE
FROM _V_DATABASE
ORDER BY DATABASE
```

The result determines the set of databases used in subsequent stages. A
database may later be marked as unavailable after a catalog error; subsequent
stages are skipped for that database.

## 2. Schemas — Once per Live Database

Source: `NZ_QUERIES.listSchemas(TEST_DB)`.

```sql
SELECT SCHEMA
FROM TEST_DB.._V_SCHEMA
ORDER BY SCHEMA
```

The query populates the database schema cache.

## 3. Object Type Groups — Once per Live Database

Source: `NZ_QUERIES.listTypeGroups(TEST_DB)`.

```sql
SELECT DISTINCT TRIM(OBJTYPE) AS OBJTYPE
FROM TEST_DB.._V_OBJECT_DATA
WHERE DBNAME = 'TEST_DB'
ORDER BY OBJTYPE
```

The result builds groups such as `TABLE`, `VIEW`, and `PROCEDURE` that are
visible in the schema tree.

## 4. Regular Objects — Once per Live Database

Source: `NZ_QUERIES.listTablesAndViews([TEST_DB])`.

```sql
SELECT * FROM (
    SELECT
        O.OBJNAME,
        O.OBJID,
        O.SCHEMA,
        O.DBNAME,
        O.OBJTYPE,
        O.OWNER,
        COALESCE(S.REFOBJNAME, '') AS REFOBJNAME,
        COALESCE(O.DESCRIPTION, '') AS DESCRIPTION
    FROM TEST_DB.._V_OBJECT_DATA O
    LEFT JOIN TEST_DB.._V_SYNONYM S ON S.OBJID = O.OBJID
    WHERE O.DBNAME = 'TEST_DB'
      AND O.OBJTYPE IN (
          'TABLE',
          'VIEW',
          'SYNONYM',
          'SEQUENCE',
          'MATERIALIZED VIEW',
          'SYSTEM VIEW',
          'GLOBAL TEMP TABLE'
      )
) TMP
ORDER BY DBNAME, SCHEMA, OBJNAME
```

This branch does not include `EXTERNAL TABLE`, does not reference
`_V_EXTERNAL`, and does not contain the `NOT EXISTS` anti-join. External tables
are fetched by a separate SQL statement.

## 5. External Tables — Once per Live Database

Source: `NZ_QUERIES.listExternalTables([TEST_DB])`.

```sql
SELECT * FROM (
    SELECT
        E1.TABLENAME AS OBJNAME,
        E1.RELID AS OBJID,
        E1.SCHEMA AS SCHEMA,
        E1.DATABASE AS DBNAME,
        'EXTERNAL TABLE' AS OBJTYPE,
        '' AS OWNER,
        '' AS REFOBJNAME,
        '' AS DESCRIPTION
    FROM TEST_DB.._V_EXTERNAL E1
    WHERE E1.DATABASE = 'TEST_DB'
) TMP
ORDER BY DBNAME, SCHEMA, OBJNAME
```

The results of this branch are combined with the results of the SQL statement
in section 4 by the extension code. Deduplication is not performed by SQL, and
there is no read from `TEST_DB.._V_OBJECT_DATA` or join to
`TEST_DB.._V_EXTOBJECT` here. The explorer omits external-table owner in the
bulk list; DDL/introspection retrieves it only when that object is inspected.

## 6. Procedures — Once per Live Database

Source: `NZ_QUERIES.listProcedures(TEST_DB)`.

```sql
SELECT SCHEMA,
       PROCEDURE,
       PROCEDURESIGNATURE,
       RESULT AS RETURNS,
       OWNER,
       DATABASE
FROM TEST_DB.._V_PROCEDURE
WHERE DATABASE = 'TEST_DB'
ORDER BY SCHEMA, PROCEDURE
```

The result is stored both under the database key and under the schema keys in
the procedure cache.

## 7. Columns of Regular Tables and Views — Once per Live Database

Sources: `NZ_QUERIES.listColumnsWithKeys(TEST_DB)`,
`NZ_QUERIES.listColumnKeyFlags(TEST_DB)`, and
`NZ_QUERIES.listColumnDistributionFlags(TEST_DB)`.

```sql
SELECT
    O.OBJID AS OBJID,
    O.OBJNAME AS TABLENAME,
    O.SCHEMA,
    O.DBNAME,
    C.ATTNAME,
    C.FORMAT_TYPE,
    C.ATTNUM,
    C.DESCRIPTION AS DESCRIPTION
FROM TEST_DB.._V_RELATION_COLUMN C
JOIN TEST_DB.._V_OBJECT_DATA O ON C.OBJID = O.OBJID
WHERE O.DBNAME = 'TEST_DB'
  AND O.OBJTYPE IN ('TABLE', 'VIEW')

SELECT K.OBJID, K.ATTNAME, K.CONTYPE
FROM TEST_DB.._V_RELATION_KEYDATA K
WHERE K.DATABASE = 'TEST_DB'
  AND K.CONTYPE IN ('p', 'f')

SELECT D.OBJID, D.ATTNAME
FROM TEST_DB.._V_TABLE_DIST_MAP D
WHERE D.DATABASE = 'TEST_DB'
```

The three scans run serially on the metadata connection. TypeScript reproduces
the former `LEFT JOIN`, `MAX`, `GROUP BY`, and `ORDER BY` semantics before the
result is grouped by table and stored in the cache. None of these operations is
performed by Netezza for the regular column snapshot. The base scan deliberately
preserves a missing description as `NULL`, matching the rows returned by the
former grouped query on live Netezza.

Database-wide refreshes read the complete per-database key and distribution
views shown above. Targeted schema/table lookups add an `OBJID IN (SELECT OBJID
FROM ..._V_OBJECT_DATA ...)` predicate to both auxiliary scans, using the same
object filters as the base scan. This prevents user-facing row limits from
silently dropping key markers for the requested object; metadata refresh also
rejects any catalog result explicitly marked as row-limited instead of caching
a partial snapshot.

## 8. External Table Columns — Conditionally, at Most Once per Database

Source: `NZ_QUERIES.listExternalColumnsWithKeys(TEST_DB)`.

This query is executed only when stage 3 detected at least one `EXTERNAL TABLE`
in `TEST_DB` and the main column branch did not end with a catalog error.

```sql
SELECT
    E1.TABLENAME AS TABLENAME,
    E1.SCHEMA AS SCHEMA,
    E1.DATABASE AS DBNAME,
    C.ATTNAME AS ATTNAME,
    C.FORMAT_TYPE,
    C.ATTNUM,
    COALESCE(C.DESCRIPTION, '') AS DESCRIPTION,
    0 AS IS_PK,
    0 AS IS_FK,
    0 AS IS_DISTRIBUTION_KEY
FROM TEST_DB.._V_RELATION_COLUMN C
JOIN TEST_DB.._V_EXTERNAL E1 ON C.OBJID = E1.RELID
WHERE E1.DATABASE = 'TEST_DB'
ORDER BY SCHEMA, TABLENAME, ATTNUM
```

The result is merged in TypeScript with the result from section 7. There is no
join to `_V_OBJECT_DATA`, `UNION ALL`, or `NOT EXISTS` here.

## Expected Number of Queries

If `N` is the number of live databases returned by `_V_DATABASE`, and `E` is
the number of those databases in which an external table was detected, then
the number of actual catalog queries for a complete, error-free refresh is:

```text
1 + 8N + E
```

Breakdown:

- `1` — database list;
- `2N` — schemas and type groups;
- `2N` — regular and external objects;
- `N` — procedures;
- `3N` — regular columns, key flags, and distribution flags;
- `E` — external-table columns, only where detected.

The technical `SELECT CURRENT_SID` from section 0 is added once, for a total
of `2 + 8N + E` generated SQL statements. Catalog or cache errors, or skipping
a dead database, may reduce the number of executions.

## Refresh Observability and Snapshot Verification

Click the `Metadata refresh …%` item in the VS Code status bar to open **Schema
Refresh Details**. The panel is read-only and shows only SQL generated by the
extension. For each refresh it provides:

- statements already executed, currently running, queued, planned, skipped,
  and failed;
- result-row counts for catalog objects (tables/views/external tables) and
  columns, plus the accumulated execution time for both groups;
- elapsed refresh time and the longest individual metadata SQL;
- `Refresh elapsed` stops at the terminal refresh event, and `Longest single
  SQL` is a monotonic maximum for that refresh (it never falls when a shorter
  statement finishes later);
- the `Repeat full metadata refresh` button on each connection card invokes
  the existing connection-scoped full-refresh command, clears that
  connection's in-memory metadata, and starts the complete Netezza prefetch;
- a status filter (`failed`, `timeout`, `running`, `slow` over five seconds,
  and the remaining states) and sorting by execution duration, queue wait, or
  start time;
- a `Copy SQL` button on every query entry for quick investigation or replay
  in a controlled SQL editor session;
- the final snapshot state. An incomplete snapshot lists missing refresh stages
  and up to 100 exact missing column-layer keys, together with their total
  count.

The Output channel includes the same SQL lifecycle as structured debug lines:

```text
[MetadataRefresh] connection=NZ state=completed kind=columns target=JUST_DATA durationMs=945 sql=...
```

When all required catalog SQL completed but an object has no matching column
layer, the refresh performs one object-catalog recheck for each affected
database. Objects that disappeared between the object and column stages are
removed. Surviving or unconfirmed objects receive an explicit empty column
layer, and the snapshot is reported as `complete with warnings`. Empty layers
are persisted, so completion, lint and other editor requests remain cache-only
instead of repeatedly starting schema work.

When a connection snapshot reaches its TTL, the connection's in-memory metadata
and persisted v3 payload are discarded before the next full refresh. The new
snapshot therefore cannot merge with stale tables left by an older
`_V_OBJECT_DATA` result; other connections' cache entries are left untouched.

`Snapshot incomplete` is reserved for a failed, timed-out or otherwise
unfinished required catalog query. An automatic failure can be retried once
after a five-minute cooldown; a second automatic failure opens the
connection-scoped circuit for the remainder of the extension-host session.
The explicit `Refresh Schema` command resets and bypasses that circuit.

When the panel reports `missing stages: objects`, the connection has no
non-empty table/view catalog layer at the final snapshot check. A `Tables /
views` value of `0 rows` means the object catalog SQL returned no rows (or was
skipped/failed); after manually clearing one connection, the refresh also
resets the old object-catalog completion markers so the object SQL is executed
again.

## SQL Queries That Are Not Part of the Full Connection Refresh

The following paths are separate operations and should not be counted as part of
the full prefetch:

- `getTableColumns(database, schema, table)` — fetches the columns of a single
  table, for example after a DDL operation or in the old object-expansion path;
- `getExternalTableColumns(database, schema, table)` — the analogous fallback
  for a single external table;
- `listColumnsWithKeys(database, { schema })` and the external variant —
  prefetches a single schema;
- `listTypeGroups(database)` called manually after refreshing a database node —
  refreshes only the type groups, not the entire connection prefetch.

If the `Fetching columns for ...` message appears after the full refresh has
finished, look for a call to one of these separate paths, a cache miss, or a
second full-prefetch trigger. The full refresh described above does not itself
execute `getTableColumns` for every table.

## Refreshing a Single Database Node

The full refresh of a server node should not be confused with the command to
refresh a single database. The latter path (`refreshSchemaSelection` for the
`database` context) invalidates the schema cache and executes only the type
groups query from section 3, then refreshes the tree view. It is not a full
prefetch of all objects and columns.

## Timing and Trigger Diagnostics

Every metadata SQL that supplies a `MetadataQueryContext` (including all full
prefetch SQL) produces one debug log entry prefixed with `[MetadataTiming]`.
For example:

```text
[MetadataTiming] source=connection-prefetch kind=columns target=TEST_DB reason=full-column-prefetch queueWaitMs=0 executeReaderMs=14 serverWaitToFirstRowMs=842 rowFetchMs=31 readerCloseMs=1 rowsRead=1240 totalMs=890 status=success sessionId=12345
```

Interpret the fields as follows:

- `queueWaitMs` — time waiting for the metadata limiter and, for a full
  refresh, the serial queue of the selected physical session. Independent
  column sessions have separate bounded queues. It is client-side waiting; the
  SQL has not started on Netezza yet.
- `executeReaderMs` — time to create the reader. It includes driver/network
  work before a result reader is available.
- `serverWaitToFirstRowMs` — time from the available reader to the first row
  (or end-of-result). This is the best client-observed approximation of how
  long Netezza/driver needed before transmitting result data; it is not a
  direct server CPU metric.
- `rowFetchMs` — time spent draining rows after the first row; a large value
  points to result volume/transfer rather than the initial catalog plan.
- `source`, `kind`, `target`, and `reason` identify why the query exists, for
  example `connection-prefetch / columns / TEST_DB /
  full-column-prefetch` or `schema-tree / table-columns / TEST_DB.ADMIN.T1`.

For Netezza completion, a cache miss is deliberately cache-only: it must not
create a live catalog query while someone types. The debug message
`Cache-only column lookup miss ... source=completion` explains an empty
completion result before prefetch completes; it is not followed by a
`Fetching columns for ...` database request. An empty cold-cache list is also
not cached for the 12-hour list TTL, so the next completion sees newly
prefetched metadata.

The read-only live split-query probe is available at
`src/__tests__/integration/netezzaPrefetchSplit.live.integration.test.ts`. It
prints `PROBE TIMING` entries with the same execute/first-row/fetch breakdown
when run against an explicitly selected test database.

## Document Scope

The list includes SQL generated by the repository for Netezza metadata. It does
not include initialization SQL executed inside the
`@justybase/netezza-driver` because it is not generated by this code, and its
list depends on the driver version and connection state.
